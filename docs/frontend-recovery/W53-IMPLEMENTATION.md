# W53：公共收银台交易 Hash 只读链上核验与安全审计

日期：2026-11-11。开发分支 `feat/w53-readonly-tx-hash-verification`。**不改变 W31，也不部署或覆盖生产 `src/www`。**

## 核心结论：验证证据不等于结算付款

现有 Go `POST /pay/submit-tx-hash/:trade_id` 会调用 `SubmitCashierManualPayment`，先校验链上转账，然后进入 `orderProcessingWithAllowedStatuses`，实际把订单状态改为 2 并触发后续父单/回调流程。它不是“预览”接口，不能仅因为浏览器显示确认按钮就当作无风险接口。

审计发现旧的 `orderProcessing` 先提交子单付款状态，再另一个事务处理父单；失败时可能出现子单=2、父单≠2，进而需要 W52 人工对账。其交易哈希去重依赖非唯一索引和应用级互斥；跨进程重复结算尚缺数据库唯一交易归属保证。因此 **W53 不从新前端调用这个结算接口**，也不宣称旧接口已通过安全验收。W54/W55 需独立修复事务原子性、扫描器和人工结算并发争用，再考虑恢复真正的公开“提交入账”操作。

## 本轮实现

- 新增独立 `POST /pay/verify-tx-hash/:trade_id`：使用现有 `ValidateManualOrderPayment`，核实交易实际网络、Token/合约、收款地址、金额、成功状态、链上时间和确认数；复用旧的规范化 Hash 及数据库重复检查。
- 仅允许数据库仍为 status=1 的 on_chain 订单。已过期、待选网络、OkPay、对账冲突、超过付款时限、父单已有子单、父单已结算或子单不唯一时拒绝。不把 `10010` 状态冲突显示成过期。
- RPC 请求前后分别读取订单及关联关系，验证期间订单变化、地址/币种/金额被改变则返回 10010。后读再次检查 Hash 是否已被其他订单入账。
- 返回严格白名单 `trade_id,verification=verified,block_transaction_id`；**不含 status=2、paid=true，不更新订单状态、父单、钱包锁或供应商订单，不发回调**。
- 收银台仅当 W52 三 GET 已核实且展示真实 on-chain 收款目标时显示输入。最多 256 字符，经用户两步确认后再做三 GET 并比对原金额、Token、网络、地址、关联关系和 SQL 状态，才发送单次 verify-only POST。
- 无论成功还是网络未知，当前收银台会话锁住重复提交，继续使用原有 GET 轮询。服务器响应“verified”仅代表链证据通过，绝不在浏览器乐观显示已付款。

## 真实 Go 错误码

| 码 | Go 语义 | 前端 |
|---|---|---|
| 10007 | 该交易哈希已被订单处理 | 重复使用，停止提交 |
| 10008 | 订单不存在 | 不提交，重新核验 |
| 10009 | 请求参数错误 | 修正格式，当前请求不执行 |
| 10010 | **订单状态冲突，非过期** | 只读刷新 |
| 10013 | 不是待付款订单 | 只读刷新 |
| 10038 | 链上交易验证失败 | 告知失败，无已付款断言 |
| 10039 | 第三方供应商订单不能使用手动链上验证 | 阻断 |

既有验证器的交易所需确认数、Token 合约、链上交易时间、收款地址和金额以 Go 服务端真实数据为准；前端不实施本地“验证通过”。

## 尚未通过的上线门槛

现有结算接口跨进程幂等、数据库唯一约束、父子订单原子性、已有 scanner 自动入账并发、真实 RPC/网络异常、浏览器 E2E、真实转账回调均需要后续 W54/W55/W60+ 验收。**不能把“Hash 证据已验证”当成“商户已到账”，不能直接部署生产 `src/www`。**
