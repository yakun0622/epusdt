# W54：数据库级交易归属与父子订单原子结算

状态：自动 Go Actions 校验中；以 PR 的最终检查结果为准。开发分支 `feat/w54-atomic-settlement-dedup`。

## 发现的风险

- 旧 `orderProcessing` 先提交子订单已支付，然后在另一事务更新父订单。进程崩溃、父状态冲突或数据库错误可能产生已支付子单 + 待支付父单。
- 旧 Hash 唯一性是数据库非唯一索引 + 进程内 `gOrderProcessingLock`，两个实例无法靠本地互斥达成全局防重。
- 旧 OkPay 回调在订单 Hash 已被其他订单处理时仍可能将当前供应商订单状态改成 `paid`，必须绑定订单归属。
- 自动链上扫描与人工 Hash 提交共同调用 `OrderProcessing`，故修复必须位于共同结算入口，而非只加强浏览器校验。

## 实施

1. 新增 `payment_tx_claim` 表，`claim_key` 为主键。以支付渠道、网络及规范化交易引用构造 SHA-256 的数据库唯一归属。Tron/EVM/Aptos 的大小写和 `0x` 别名规范化；TON、Solana、OkPay 标识保留大小写（不作未经验证的等价推断）。
2. 在同一主数据库事务中执行：锁父单（子单再锁本单）→ 校验状态及收款目标 → 检查历史订单重复 Hash → 创建唯一归属 claim → 修改实际付款订单 → 修改父单 `pay_by_sub_id` → 过期同父其他子单及其本地供应商状态 → 提交。主事务设置 20 秒数据库超时，任何 SQL 错误或超时必须回滚整个事务，不产生半支付订单或已提交 claim。
3. 数据库唯一主键跨进程生效；`FOR UPDATE` 锁支持 MySQL/Postgres，SQLite 采用数据库写锁语义。不要把单实例 Mutex 当成跨实例保证。
4. 结算前请求中的 Token、network、收款地址、实际金额必须与持久化订单一致，拒绝竞态改变支付目标。链上 RPC 真实性、合约、到账确认、交易时间继续由原验证器和自动扫描器各自负责；W54 不创建绕过真实链验证的新入口。
5. 支付回调只由父单排队；子单回调标为无需发送。运行时钱包预留锁属于独立 SQLite 数据库，在主事务成功后按 trade_id 执行释放，避免迟到的清理删除其他新订单的预留锁；释放失败只告警、不可再次结算或假定数据库回滚。
6. 对已经存在的老订单，结算事务仍查询 `orders.block_transaction_id` 并识别主流十六进制编码别名；不需要修改历史订单状态、不自动补单、不自动重发回调。新增 claim 只对后续真实结算持久创建。
7. OkPay 验签与订单、币种、金额验证继续有效；本地供应商状态和实际付款记录在同一主事务内写入。仅当前订单已经使用同一供应商订单 ID 成功结算时，才把重复回调视为已处理；不得误认其他订单的 Hash。
8. `10007` 表示交易已使用，`10010` 表示结算状态冲突（**不是订单过期**）；并发冲突不得重复发通知。
